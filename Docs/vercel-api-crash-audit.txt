# Vercel API Crash Audit

Date: 2026-05-12
Project: MCA King / Brokerage CRM
Scope: Audit only. No code changes were made to application/runtime files.

## 1. Executive Summary

The current Vercel production API crash is consistent with a serverless module-resolution / packaging failure, not a Supabase credential failure.

The live error reported from Vercel is:

```txt
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/var/task/src/server/api' imported from /var/task/api/index.js
```

The exact import in the current single Vercel function is:

```ts
import { handleApiRequest } from '../src/server/api'
```

This is an extensionless relative TypeScript import. It works in local Bun/Vite/TypeScript tooling, but Vercel's deployed Node ESM runtime is trying to resolve `/var/task/src/server/api` as a runtime JavaScript module and cannot find it.

Most likely root cause: the previous consolidation into a single `api/index.ts` function introduced a runtime import from the Vercel function into `src/server/api` that Vercel did not bundle or did not rewrite into a resolvable JavaScript file path.

## 4. Current `api/index.ts`

```ts
import type { VercelRequest, VercelResponse } from '@vercel/node'
import { handleApiRequest } from '../src/server/api'

export const config = {
  api: {
    bodyParser: false,
  },
}

async function readRequestBody(req: VercelRequest): Promise<BodyInit | null> {
  if (req.method === 'GET' || req.method === 'HEAD') return null

  const chunks: Buffer[] = []
  for await (const chunk of req) {
    chunks.push(Buffer.isBuffer(chunk) ? chunk : Buffer.from(chunk))
  }

  return chunks.length > 0 ? Buffer.concat(chunks) : null
}

function getRequestHeaders(req: VercelRequest): Headers {
  const headers = new Headers()

  for (const [key, value] of Object.entries(req.headers)) {
    if (value === undefined) continue
    headers.set(key, Array.isArray(value) ? value.join(', ') : String(value))
  }

  return headers
}

function getOriginalApiPath(req: VercelRequest): string {
  const routedPath = req.query.path
  const path = Array.isArray(routedPath)
    ? `/api/${routedPath.join('/')}`
    : typeof routedPath === 'string' && routedPath.length > 0
      ? `/api/${routedPath}`
      : '/api'

  const searchParams = new URLSearchParams()
  for (const [key, value] of Object.entries(req.query)) {
    if (key === 'path' || value === undefined) continue
    if (Array.isArray(value)) {
      value.forEach(item => searchParams.append(key, item))
    } else {
      searchParams.set(key, value)
    }
  }

  const queryString = searchParams.toString()
  return queryString ? `${path}?${queryString}` : path
}

function getRequestUrl(req: VercelRequest): string {
  const protocolHeader = req.headers['x-forwarded-proto']
  const protocol = Array.isArray(protocolHeader) ? protocolHeader[0] : protocolHeader ?? 'https'
  const host = req.headers.host ?? 'localhost:3000'
  return `${protocol}://${host}${getOriginalApiPath(req)}`
}

async function sendWebResponse(res: VercelResponse, response: Response): Promise<void> {
  res.status(response.status)
  response.headers.forEach((value, key) => {
    res.setHeader(key, value)
  })

  res.send(Buffer.from(await response.arrayBuffer()))
}

export default async function handler(req: VercelRequest, res: VercelResponse): Promise<void> {
  try {
    const request = new Request(getRequestUrl(req), {
      method: req.method,
      headers: getRequestHeaders(req),
      body: await readRequestBody(req),
    })

    await sendWebResponse(res, await handleApiRequest(request))
  } catch (error) {
    if (error instanceof Response) {
      await sendWebResponse(res, error)
      return
    }

    console.error(error)
    res.status(500).json({ error: 'Internal server error' })
  }
}
```

Critical line:

```ts
import { handleApiRequest } from '../src/server/api'
```

## 5. Current `vercel.json`

```json
{
  "buildCommand": "bun run build",
  "outputDirectory": "dist",
  "framework": "vite",
  "rewrites": [
    { "source": "/api/:path*", "destination": "/api?path=:path*" }
  ]
}
```

This rewrite is designed to route all `/api/*` paths into the one `api/index.ts` function while preserving the original path in `req.query.path`.

The rewrite is not the direct source of the reported crash. The crash occurs after Vercel reaches `api/index.js` and tries to import `../src/server/api`.

## 6. Current Package / Module Settings

From `package.json`:

```json
{
  "type": "module",
  "scripts": {
    "dev": "vite --config \"$PWD/vite.config.ts\"",
    "build": "vite build --config \"$PWD/vite.config.ts\"",
    "preview": "vite preview --config \"$PWD/vite.config.ts\""
  },
  "dependencies": {
    "@vercel/node": "^5.8.0"
  }
}
```

Important point:

- `"type": "module"` means emitted `.js` files run as ESM.
- Node ESM is strict about relative import resolution.
- A runtime import like `../src/server/api` is not resolved the same way Bun/Vite/TypeScript resolve it locally.

From `tsconfig.json`:

```json
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "bundler",
    "allowImportingTsExtensions": true,
    "noEmit": true
  }
}
```

Important point:

- `moduleResolution: "bundler"` is optimized for tools like Vite/esbuild/Rollup.
- `noEmit: true` means the project's TypeScript config does not emit server JavaScript for `src/server/api.ts`.
- Vercel's Node function builder must independently trace/bundle/compile the function dependency graph.

## 7. Lockfile / Install Risk

There are two lockfiles present:

```txt
bun.lock
package-lock.json
```

Findings:

- `bun.lock` includes `@vercel/node`.
- `package-lock.json` appears stale and does not include `@vercel/node` in its root dependencies or package entries.
- `package.json` has no `packageManager` field.

Risk:

- If Vercel chooses npm because `package-lock.json` exists, installs can differ from local Bun installs.
- However, the reported error is specifically `ERR_MODULE_NOT_FOUND` for `/var/task/src/server/api`, not `Cannot find package '@vercel/node'`.
- So stale lockfiles may be a secondary deployment hygiene issue, but not the most direct explanation of this crash.

## 8. Central API Router Import Graph

`src/server/api.ts` imports many route modules using extensionless relative imports, for example:

```ts
import { GET as getMerchants, POST as postMerchants } from '../routes/merchants/index'
import { GET as getMerchant, PATCH as patchMerchant, DELETE as deleteMerchant } from '../routes/merchants/[id]'
import { POST as registerAuth } from '../routes/auth/register'
import { POST as loginAuth } from '../routes/auth/login'
import { GET as meAuth } from '../routes/auth/me'
import { POST as aiChat } from '../routes/ai/chat'
import type { RouteContext } from '../lib/route-utils'
```

A scan found approximately 139 extensionless relative imports under:

```txt
api/
src/server/
src/routes/
src/lib/
```

This matters because even if the first import in `api/index.ts` were fixed, a non-bundled Node ESM runtime may then fail on the next extensionless import inside `src/server/api.ts` or one of its dependencies.

In other words, the immediate error points at `api/index.ts`, but the broader pattern is that the server route tree is written in bundler-style TypeScript imports, not plain Node ESM runtime imports.

## 9. Server Code Pulls in Frontend Component Module

`src/lib/data-shapes.ts` imports a value from a frontend component-area file:

```ts
import { DEFAULT_APPLICATION_STATUS } from '../../components/dashboards/shared/applicationStatus'
```

That file is mostly constants/helpers, but it lives under `components/` and also exports UI class helper strings.

Risk:

- This is not the current reported missing module.
- But it makes the server dependency graph less clean.
- A serverless function bundle ideally should avoid importing from frontend component directories.
- A future fix could move shared status constants into a neutral shared/server-safe module.

## 10. Previous Fixes That Are Probably Not the Current Root Cause

Earlier suspected issues were addressed:

- Email config was made lazy so missing Resend vars do not crash auth routes at module import time.
- Supabase server client was made lazy so importing the central router does not immediately throw if env vars are missing.
- Gemini key was moved server-side and removed from public `VITE_` exposure.

The current Vercel log is not an env-var crash. It is a module load crash before request handling.

## 11. Root Cause Assessment

### Most likely root cause

The single Vercel function imports the existing TypeScript central router through an extensionless path:

```ts
import { handleApiRequest } from '../src/server/api'
```

In production, Vercel emitted/ran `api/index.js`, and Node ESM tried to resolve:

```txt
/var/task/src/server/api
```

That path did not exist as a resolvable runtime module.

This can happen if:

1. Vercel did not bundle `src/server/api.ts` into `api/index.js`.
2. Vercel did not copy/transpile `src/server/api.ts` into `/var/task/src/server/api.js`.
3. Vercel preserved the extensionless import in emitted JavaScript, which Node ESM cannot resolve as written.
4. The Vercel builder is treating the imported file tree as external/source files instead of fully bundling them.

### Less likely root causes

- Bad Supabase env vars: less likely for this exact error because the import fails before DB access.
- Bad Vercel rewrite: less likely because the error proves `api/index.js` is being invoked.
- Hobby function count: already reduced to one function file.
- Resend/Gemini env vars: unlikely for this exact error.

## 12. Fix Options to Evaluate Later

No code changes were made during this audit. These are possible paths to evaluate in a fix session.

### Option A — Add `.js` extensions throughout the server-side import graph

Change runtime imports to Node ESM-compatible `.js` specifiers, starting with:

```ts
import { handleApiRequest } from '../src/server/api.js'
```

But this cannot stop at `api/index.ts`. Because `src/server/api.ts` and route/lib files have many extensionless imports, the server dependency graph would likely need `.js` specifiers throughout all runtime imports.

Pros:

- Aligns source with Node ESM semantics.
- No bundler required if Vercel copies/transpiles files correctly.

Cons:

- Many files touched.
- TypeScript config must support `.js` specifiers pointing at `.ts` source.
- Easy to miss imports.

### Option B — Bundle the API server into one serverless entry before Vercel runs it

Use a bundler such as esbuild/tsup/rollup to compile the catch-all API plus its route tree into a Vercel-compatible single JavaScript entry.

Pros:

- Avoids changing 100+ import specifiers.
- Bundler can resolve extensionless TypeScript imports.
- Keeps one Vercel function.

Cons:

- Requires build pipeline changes.
- Need to ensure Vercel uses the bundled function output, not the raw TypeScript file.
- Must verify dependencies like Supabase, Resend, Gemini, and Better Auth utilities bundle correctly.

### Option C — Move the central API router into `api/index.ts` or an `api/`-local bundled module

This would reduce cross-directory tracing from `api/` into `src/`, but still has to solve route imports.

Pros:

- Keeps Vercel function entry self-contained.

Cons:

- Could duplicate or muddy architecture.
- Does not automatically solve extensionless imports deeper in the graph unless bundled.

### Option D — Use a dedicated backend/runtime instead of Vercel functions

Host the server router in a Node service, edge-compatible server, or another backend platform.

Pros:

- Avoids Vercel Hobby function packaging constraints.

Cons:

- Larger deployment change.
- Not ideal if current goal is Vercel Hobby compatibility.

## 13. Recommended Fix Direction

Recommended direction: **Option B, bundle the catch-all API function**, or a carefully implemented variant of it.

Reason:

- The server route tree uses bundler-style imports extensively.
- Local dev already relies on Vite/Bun/TypeScript resolving extensionless imports.
- Trying to make raw Node ESM resolve every existing route import may require broad code churn.
- A bundled serverless entry better matches how the code is currently authored.

Second-best direction: **Option A**, but only if applied consistently to the full server import graph and verified with a production-like Node ESM build.

## 14. Verification Checklist for Any Future Fix

After a fix is implemented, verify all of the following:

```bash

```

Then deploy to Vercel and test:

