# Goose Agent Prompt — Phase H: Compliance + Audit Hardening

> Phases A through G are complete. MCA King now has activity/tasks, lender offer isolation, funded deals + broker revenue + internal sales rep commissions, merchant-file submissions, search/saved views, account settings/admin user management, Renewals, payoff request tracking, dynamic funding history, and Reporting/Analytics. Phase H hardens the CRM for production handling of sensitive merchant data by adding audit logs, endpoint authorization review, document/file security, sensitive-data masking, security headers, and production browser hardening.

---

## Business Model Rules — Read Before Writing Anything

MCA King is a **broker-shop CRM**, not a lender-originated deal marketplace.

```txt
Admin = broker shop owner/operator
Sales Rep = internal broker-shop rep
Merchant = funding applicant/customer
Lender/Funder = external funding company reviewer/approver
```

Hard business rules:

```txt
Lenders do not submit merchant deals into MCA King.
Lenders review merchant files that the broker shop submits/matches to them.
Admin represents the broker shop owner/operator.
Sales reps are internal broker-shop reps.
Lender-side account/relationship managers are lender contacts only.
No ISO payout model.
No referral partner model.
No outside broker commission model.
No lender-side manager payout model.
```

For Phase H specifically:

```txt
Security must be enforced server-side, not only by hiding UI.
Audit logs must not expose passwords, tokens, service-role keys, full SSNs, or full bank/document content.
Lenders/funders must never see competing lender/funder data, broker revenue, sales rep commissions, or broker strategy.
Merchants must only see their own merchant/application data.
Sales reps must only see assigned/permitted merchant files and their own scoped reporting/commissions.
Admins can see broker-shop-wide data, but sensitive fields should still be masked by default where practical.
```

## Step 2 — Database Schema

### 2.1 Create `audit_logs`

Create:

```sql
create table if not exists public.audit_logs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references public.users(id) on delete set null,
  action text not null,
  entity_type text,
  entity_id uuid,
  ip_address text,
  user_agent text,
  metadata jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);

create index if not exists audit_logs_user_created_idx on public.audit_logs(user_id, created_at desc);
create index if not exists audit_logs_entity_idx on public.audit_logs(entity_type, entity_id, created_at desc);
create index if not exists audit_logs_action_created_idx on public.audit_logs(action, created_at desc);
create index if not exists audit_logs_created_idx on public.audit_logs(created_at desc);

alter table public.audit_logs enable row level security;

create policy "block_public_audit_logs"
on public.audit_logs for all using (false);
```

Important:

```txt
Only server-side service-role routes should write/read audit logs.
Normal frontend Supabase clients should not access audit_logs directly.
```
